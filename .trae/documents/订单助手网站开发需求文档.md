# 订单助手网站 —— 开发需求文档

> 版本：v1.0  状态：需求已确认
> 用途：本文件是可直接交给 Agent 进行开发的完整需求文档，包含需求、技术方案、数据模型、接口与页面规范、验收标准。

---

## 1. 项目概述

### 1.1 背景
为「开学季校园二手图书配送」场景打造一个订单助手网站。一个 3 人小团队（含用户本人）共享使用，**不登录账号**，三人共同使用同一份实时同步的订单数据。

### 1.2 目标
- 团队成员都能在任何设备上**实时看到**其他人录入、修改的订单。
- 用**预定配送时间**驱动配送流程，自动呈现配送优先级。
- 配送员按**配送区域（苑+编号）**批量处理订单、导出配送清单。
- 内置**书籍名称记忆**功能，减少同类图书重复录入。
- 实时统计每种书在所有订单中的数量，方便备货。

### 1.3 当前范围 / 非目标（本次不做）
- 不做登录、注册、账号体系、权限区分（三人共享 + 顾客下单页均无需登录）。
- 多一个**对外分享的下单页**：可把链接发给顾客，顾客自助填单提交，订单实时进入你的后台列表。
- 不做支付、书籍库存管理、供应商/进货管理。
- 不做多订单合并配送（一期按单配送即可）。

## 2. 技术架构（已确认）

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | 静态 HTML/CSS/JS（单页应用，原生或轻框架如 Vue3 CDN） | 部署到 GitHub Pages |
| 后端 | Cloudflare Workers | 提供 REST API |
| 数据库 | Cloudflare D1（SQLite） | 存订单与明细，共享数据 |
| 同步机制 | **定时轮询**：前端每 3~5 秒自动拉取最新订单 | 三人共享、数据量小，轮询足够实时 |

架构说明：
- 前端是纯静态站点，通过 `fetch` 调用 Workers API 读写 D1。
- 所有数据存在共同的 Cloudflare D1 里，因此天然实现「三人共享 + 实时同步」。
- 不加鉴权（需求确认不做登录）。提示：Workers 地址为公开 URL，任何知道地址的人都可访问，作为已知限制，后续如需要可加共享口令。

## 3. 功能模块总览

1. **订单表单**：新增/编辑订单，含配送区域、预定时间、联系方式、备注、书单明细（可增删改）。
2. **订单列表**：展示全部订单，按预定配送时间由近到远排序；已完成订单置灰变淡。
3. **订单状态流转**：待配送 → 配送中 → 已完成。
4. **配送区域选择**：大苑（4 个）下挂 4 个编号，二级下拉联动。
5. **书籍名称记忆**：表单输入书名时，从历史书名中去重联想，可快速点选。
6. **统计面板**：统计每种书在所有订单（**含已完成**）中的总数量。
7. **历史订单**：已完成订单保留可查看，支持一键清空历史。
8. **配送清单导出**：按区域生成当天/待配送的清单（可打印/导出）。
9. **四大配送区域独立页面**：首页展示 4 个大苑入口，点进某苑只显示该苑（可按编号再筛）的订单，方便专人对接固定区域配送。
10. **移动端优先适配**：主要面向手机端使用，所有页面在手机尺寸下布局自适应、触控友好。
11. **顾客自助下单页（对外分享）**：一个独立、精简的公开表单页，可把链接发给顾客自助填单；提交后订单实时进入三人共享的后台列表。

## 4. 数据模型（Cloudflare D1 / SQLite）

### 4.1 表 `orders`（订单主表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK AUTOINCREMENT | 订单 ID |
| delivery_building | TEXT NOT NULL | 大苑，取值：`大千苑18栋`、`长江苑19栋`、`大洲苑21栋`、`培伦苑20栋` |
| sub_zone | TEXT NOT NULL | 编号，如 `18-1`、`18-2`、`18-3`、`18-4` |
| deliver_time | TEXT (ISO datetime)，**可空** | 预定配送时间；为空表示“尽快配送” |
| contact | TEXT | 客户联系方式（手机号/QQ/微信，自由文本） |
| remark | TEXT | 配送备注（可空），如“放门口”“打电话再上” |
| status | TEXT NOT NULL | `pending`待配送 / `delivering`配送中 / `done`已完成，默认 `pending` |
| created_at | TEXT NOT NULL | 创建时间 |
| updated_at | TEXT NOT NULL | 最近更新时间 |

### 4.2 表 `order_items`（订单明细：书 + 数量）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK AUTOINCREMENT | 明细 ID |
| order_id | INTEGER FK → orders.id | 所属订单 |
| book_name | TEXT NOT NULL | 书籍名称 |
| quantity | INTEGER NOT NULL DEFAULT 1 | 数量（≥1） |

> 书籍名称记忆：不单独建表。前端下拉联想数据由 `SELECT DISTINCT book_name FROM order_items ORDER BY COUNT(*) DESC` 派生，天然全局同步、免额外维护。

### 4.3 建表 SQL（供 Agent 参考）

```sql
CREATE TABLE IF NOT EXISTS orders (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  delivery_building TEXT NOT NULL,
  sub_zone TEXT NOT NULL,
  deliver_time TEXT,
  contact TEXT DEFAULT '',
  remark TEXT DEFAULT '',
  status TEXT NOT NULL DEFAULT 'pending',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS order_items (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  order_id INTEGER NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  book_name TEXT NOT NULL,
  quantity INTEGER NOT NULL DEFAULT 1
);

CREATE INDEX IF NOT EXISTS idx_orders_deliver_time ON orders(deliver_time);
CREATE INDEX IF NOT EXISTS idx_orders_status ON orders(status);
CREATE INDEX IF NOT EXISTS idx_items_order ON order_items(order_id);
```

## 5. 后端 API（Cloudflare Workers + D1）

工作方式：Workers 通过环境变量绑定 D1，绑定名 `DB`。使用 D1 bindings，删除/更新用 `return db.prepare(...).bind(...).run()`。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/orders` | 返回所有订单（含明细）。可选 `?status=` 过滤。排序规则：`deliver_time` 为空（尽快配送）优先级最高，其次按 `deliver_time ASC`；`done` 状态恒排最末。 |
| POST | `/api/orders` | 新增订单（含明细数组）。校验必填项：区域、联系方式、书单明细；`deliver_time` 可空。返回新订单（含 id）。 |
| GET | `/api/orders/:id` | 查询单个订单（含明细）。 |
| PUT | `/api/orders/:id` | 更新订单信息+明细（整体覆盖明细）。 |
| PATCH | `/api/orders/:id/status` | 仅更新状态。body：`{ "status": "pending|delivering|done" }` |
| DELETE | `/api/orders/:id` | 删除订单（级联删除明细）。 |
| POST | `/api/clear-done` | 清空所有 `done` 状态订单（含明细）。返回删除条数。 |
| GET | `/api/book-names` | 返回去重书名+使用次数，供联想（等价于 `SELECT DISTINCT`）。 |
| GET | `/api/stats` | 返回每种书的总数量（**全部订单含已完成**求和）。返回 `[{book_name, total_quantity}]`。 |

请求/响应约定：
- 请求体为 JSON。
- 成功 HTTP 200；校验失败 HTTP 400；未找到 HTTP 404；异常 HTTP 500。
- 统一响应结构：`{ "ok": true, "data": ... }` / `{ "ok": false, "error": "msg" }`。

## 6. 前端页面与交互规范

部署于 GitHub Pages，单页应用（SPA）。底部/顶部导航切换：「区域配送 / 订单列表 / 新建订单 / 统计 / 历史」。**默认首页为「区域配送」视图**。

### 6.0 区域配送主页（首页）
- 用**网格卡片**展示 4 个大苑入口：`大千苑18栋` / `长江苑19栋` / `大洲苑21栋` / `培伦苑20栋`。
- 每张卡片显示：大苑名称、该苑当前待配送订单数（角标，实时刷新）、图标。
- **点击某苑卡片 → 进入该区域内订单页**，只展示该 `delivery_building` 的订单。
- 区域内订单页顶部可按编号（18-1…18-4）筛选，也可查看全部；仍按预定配送时间排序、状态置灰规则不变。
- 适合「专人负责某苑」：可把链接发给对应配送员（或固定该苑视图），只处理本区域单子。

### 6.1 新建/编辑订单表单（核心）
字段：
1. **配送区域（二级联动下拉）**：
   - 大苑：`大千苑18栋` / `长江苑19栋` / `大洲苑21栋` / `培伦苑20栋`
   - 编号：选定大苑后显示对应 4 个编号，如 `18-1`,`18-2`,`18-3`,`18-4`；`19-1`…`19-4`；`20-1`…`20-4`；`21-1`…`21-4`。编号严禁跨苑混用。
2. **预定配送时间**：datetime 输入（年-月-日 时:分）。
3. **客户联系方式**：手机号/QQ/微信，文本输入，可填空。
4. **备注**：文本输入（可空）。
5. **书单明细（可增删改的列表）**：
   - 每行 = 书名 + 数量；支持「添加一行」「删除本行」。
   - **书名输入框为联想输入**：聚焦/输入时下拉展示历史书名（来自 `/api/book-names`），点击即填入书名；也可手动输入新书名。
   - 数量默认为 1，最小 1。校验：一行必须有书名且数量 ≥ 1；至少保留一行。
- 提交按钮：新增 → POST；编辑 → PUT。

### 6.2 订单列表（主视图）
- 展示所有订单，**按预定配送时间从近到远排序**；`done` 状态统一排到最末。
- 每张卡片显示：配送区域（苑+编号）、预定时间、状态、联系人、备注、书的清单（书名×数量）、创建/更新时间。
- **状态标签**颜色区分：待配送=强调色、配送中=进行中色、已完成=灰色。
- **已完成订单视觉置灰变淡**（`opacity`/灰色调，弱化显示），但仍可见可点开查看。
- 卡片操作：更改状态（待配送/配送中/已完成 切换）、编辑、删除（删除需确认）。
- 顶部工具区提供「分享下单链接」按钮：一键复制顾客自助下单页 URL，便于发给同学下单。
- 顶部提供状态/区域筛选与搜索（锦上添花，实现尽量简单）。
- **自动刷新**：每 3~5 秒静默轮询 `/api/orders` 更新列表；轮询期间不打断用户正在编辑的表单。

### 6.3 统计面板
- 展示 `/api/stats` 数据：每种书及其在所有订单（含已完成）中的总数量。
- 以**卡片列表**展示，按数量降序；设计美观（圆角卡片、图标、悬浮效果，图标用开源库如 Bootstrap Icons）。
- 手动刷新 + 每次进入自动刷新。
- 支持按书名搜索/过滤（轻量实现即可）。

### 6.4 历史订单视图
- 筛出 `status = done` 的订单展示，可回看明细。
- 顶部「清空已完成」按钮 → 调 `/api/clear-done`，需二次确认，防误删。

### 6.5 配送清单导出
- 一键导出当前（待配送 + 配送中）订单，按**大苑分组**，每组下列出订单（联系人、时间、书名×数量、备注）。
- 两种方式：`window.print()` 打印友好排版；或导出 CSV（用 `Blob` 下载）。
- 目的：配送员拿清单按区域逐单送达，支持勾选已送（完成后在系统标记）。

### 6.6 顾客自助下单页（对外分享，独立页面）
> 与后台 SPA 完全分离，是一个精简的公开表单页（建议独立的 HTML 文件，如 `order-entry.html`）。

- **入口**：由后台「分享」按钮复制链接，或直接分享固定下单页 URL。顾客打开即是一张下单表单，**看不到**后台任何列表/统计/其它订单。
- 表单字段：
  1. **配送区域（二级联动）**：大苑 + 编号（顾客选择自己宿舍所在苑，如 `大千苑18栋` + `18-2`）。
  2. **姓名/收件备注（可选）**：方便配送时称呼（需求内属于可留空的文本，最终以「备注」字段存储）。
  3. **预定配送时间**：原生 datetime 选择器，缺省为空时默认尽快配送（时间为空则后台列表排序时排在最早/插队）。
  4. **联系方式**：手机号/QQ/微信，必填（用于配送联系）。
  5. **书单明细**：书名 + 数量，可加行/删行，至少一行且书名、数量有效。
  6. **书名联想**：同样走 `/api/book-names`，历史书名可点选（与后台共享记忆，越用越准）。
- 提交 → `POST /api/orders`，`status` 默认 `pending`，`delivery_building`/`sub_zone` 由顾客选择。
- 提交成功后：向顾客展示「下单成功，等待配送」的确认页/提示，不返回后台。
- 移动端优先：该页面主要被顾客用手机打开，按钮/输入控件触控友好，无多余导航。
- 反刷限制（轻量即可）：可在服务端/前端做简单时间间隔或重复提交提示，避免同一顾客反复提交（一期可仅前端提示）。
- 公开性说明：无鉴权，拿到链接即可下单。可在后台「分享」面板编辑自定义欢迎语/提示文案（可选，一期可仅固定文案）。

## 7. 视觉设计约定
- 配色：清爽、校园感，主色取青色/蓝绿系，状态色区分明显。
- 卡片式布局 + 图标 + 悬浮效果（贴合用户偏好）。
- 图标使用开源库 **Bootstrap Icons**（不用 emoji 做图标）。
- **移动端优先**：布局以手机尺寸为基准设计（最小适配 375px 宽），平板/桌面可见更多信息但保持可用。要点：
  - 响应式：使用相对单位、弹性布局（flex/grid），`meta viewport` 正确设置。
  - 触控友好：按钮/下拉/卡片点击区域 ≥ 44px，可点元素有明确反馈；表单控件适配移动端键盘（datetime 用原生控件）。
  - 导航在手机端紧凑排列（图标+短文字，或底部 Tab 导航更便于单手操作）。
  - 订单卡片在窄屏下信息不溢出、可换行；统计与区域卡片自动降为一列。

## 8. 验收标准（Agent 实现完成后逐条核验）

1. 新增订单：填表提交后，API 返回成功，列表能立即看到。
2. 编辑订单：改区域/时间/联系人/书单，保存后列表更新。
3. 状态流转：待配送 → 配送中 → 已完成 可切换；完成后卡片灰色变淡、排序移到最末。
4. 排序：列表按预定配送时间由近到远；已完成恒在最末。
5. 二级联动：选大苑后编号只能出现对应 4 个（互不混用）。
6. 书单增删改：可加行、删行、改书名改数量；空书名或无数量行被拦截。
7. 书名联想：输入书名可出现历史书名供点选，新增书名后再次输入能联想出来。
8. 统计：面板显示的每种书数量 = 全部订单（含已完成）qty 求和，准确。
9. 历史清空：点「清空已完成」并确认后，done 订单消失。
10. 同步：A 设备新增/改单，3~5 秒内 B 设备列表自动更新。
11. 导出：能打印出按大苑分组的配送清单；或能下载 CSV。
12. 联系人与备注：可填、可存、可显示。
13. 区域配送页：首页展示 4 个大苑卡片及待配送角标数量；点击某苑只显示该苑订单；区域内可按编号筛选。
14. 移动端适配：在 375px 手机宽度下所有页面内容不横向溢出、按钮/卡片可正常点击、导航可操作；在桌面下同样正常。
15. 顾客下单页：独立分享链接打开为纯表单页，无后台内容；顾客填单提交后，后台列表 3~5 秒内自动出现该订单，状态为待配送；订单可正常编辑/配送/完成。

## 10. 已知限制与后续方向
- 无鉴权：包括后台与顾客下单页均为公开 URL（已确认一期接受）。后台地址请勿外发；顾客下单地址本就对外，若被恶意刷单，一期仅靠前端/轻量服务端提示缓解。后续可加简单令牌分流后台。
- 轮询实时性：3~5 秒，已满足 3 人团队；后续如需毫秒级可升级 WebSocket。
- 并发覆盖：多人同时编辑同一订单存在后写覆盖前写的可能，一期接受，靠轮询刷新减风险。
